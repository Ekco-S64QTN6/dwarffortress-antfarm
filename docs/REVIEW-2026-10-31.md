# Repository review — 2026-10-31

## Scope and method

Reviewed the current `main` tree of
[`Ekco-S64QTN6/dwarffortress-antfarm`](https://github.com/Ekco-S64QTN6/dwarffortress-antfarm)
against the prior Antfarm review and handoff prompt. Read the repository's
`AGENTS.md`, `CLAUDE.md`, `README.md`, `docs/ROADMAP.md`,
`docs/AUTOMATION-GAPS.md`, the relevant Python/Lua modules, and the existing
test runner. Checked DFHack 0.47.05 documentation, the upstream Quickfort/Dreamfort
library guide, df-ai, the OBS WebSocket documentation, and the current
`dwarf_fortress_mcp` implementation-status statement.

This is primarily a source review, not a live-fort certification. A separate
operator-run, read-only disposable-save smoke probe was recorded on 2026-10-31
(DF 0.47.05 linux64 / DFHack 0.47.05-r8); see
[the live-smoke record](LIVE-SMOKE.md). That probe verifies selected report
entrypoints and exact loaded-save identity only. It does not qualify production
completion, mutating automation, direct-memory writes, screens, or squad creation
on a running game.

## Executive summary

The pasted review materially predates the repository's current architecture.
Antfarm already has a protocol-2 structured game-state snapshot, a file-based
command spool with atomic replacement, a Dreamfort/Quickfort blueprint runner,
several fortress automation modules, and meaningful camera hysteresis. A number
of the earlier findings therefore need to be narrowed rather than implemented
literally.

The strongest immediate reliability problems were not the ones phrased in the
old P0 list:

1. Claim writes already used an atomic temporary-file rename, but callers ignored
   write failures and claimed success. This was fixed in
   [PR #3](https://github.com/Ekco-S64QTN6/dwarffortress-antfarm/pull/3).
2. A malformed claims JSON file was reset to an empty in-memory registry. A
   later claim could overwrite the only recoverable copy. The follow-up is in
   [PR #4](https://github.com/Ekco-S64QTN6/dwarffortress-antfarm/pull/4).
3. The repository had a test runner but no GitHub Actions workflow. CI was added
   in [PR #2](https://github.com/Ekco-S64QTN6/dwarffortress-antfarm/pull/2).

## Prior findings: validation

| Prior finding | Assessment | Current evidence and decision |
| --- | --- | --- |
| No structured game-state ingestion layer | **Rejected as stated; future refinement remains** | `antfarm_server.lua` publishes `protocol = 2`, map state, fortress stats, citizen profiles, announcements, build progress, subsystem summaries, and watchdog status in structured JSON. Python consumes this state through `DFClient`. This is a real versioned snapshot API, not a transactional/replayable semantic command plane; the review conflated those two things. |
| No military automation | **Partly valid; README corrected** | `antfarm_military.lua` reports squads, enlists into existing squads, and retunes training schedules. `antfarm_defence.lua` and `antfarm_lever.lua` cover traps/restraints and event-driven lever pulls. But `create_squad()` is deliberately manual and high-risk, and the roadmap says it still needs a live-fort check. There is no fully verified tactical response or burrow-evacuation policy. |
| Blueprint success is only tile-count based | **Valid gap** | The 22-step plan gates on outstanding digging/construction and counts Quickfort's effective tile changes, with retries and warnings. It does not assert semantic outcomes such as a farm plot being plantable, a stockpile existing with the expected flags, or a room being usable. Keep the Quickfort/Dreamfort driver; add postconditions around its outputs. |
| No graceful degradation for bundled external tools | **Partly valid, lower priority** | The desktop utilities are launched separately from the core bridge and are not supervised/restarted by a common process manager. The evidence does not show that their failure blocks the Lua/Python automation loop. Treat this as operator-experience hardening, not a core-loop P0. |
| Twitch is tightly coupled to the core event loop | **Mostly stale** | Twitch is optional at TUI startup, initialization failures are caught, game-round-trip commands use a bounded worker pool, and handler exceptions are logged. It remains in the same Python process, so process-level isolation is not absolute, but the chat bridge is no longer a synchronous dependency of the Director's state loop. |
| No live-game integration tests | **Partly addressed; production integration gap remains** | PR #16 added an opt-in, read-only disposable-save harness, and PR #19 records a successful run against `region_smoke` on DF 0.47.05 / DFHack 0.47.05-r8. This verifies loaded-save identity and three report paths, not job creation, production completion, mutation, all blueprint steps, or long-run survival. A controlled mutating test campaign remains a valid gap; keep it opt-in and separate from no-game CI. |
| No fuzz/property tests for the blueprint planner | **Valid gap** | Existing tests are deterministic examples and synthetic geology fixtures. No property-based generator currently explores geological surveys, map boundaries, or combinations of gate states. |
| Claims/state files are not written atomically | **Rejected as stated; related failure handling fixed** | `ClaimRegistry._save()` already wrote `claims.json.tmp` then used `os.replace()`; the DFHack state writer similarly uses a temporary file and rename. The real bugs were ignored write errors (PR #3) and resetting a corrupt claims file before a later rewrite (PR #4). |
| README is too long and mixes tutorial/reference/changelog | **Partly valid** | The README is still several hundred lines, but the repo has already split the roadmap, fortress-build guide, checklist, modding notes, and research references into separate files. The running instructions are already a compact section; a wholesale README rewrite is not a P0. |
| Roadmap is only a link, not a living document | **Rejected as stated; README status summary could improve** | `docs/ROADMAP.md` is a real backlog with verified, unverified, and not-implemented sections, risk notes, and a suggested order. The README links to it but does not summarize the current milestone. |
| Authorship note needs a human/AI workflow guide | **Optional improvement, not a correctness defect** | The README and LICENSE transparently preserve the existing Claude/human authorship note. A CONTRIBUTING guide could explain review expectations for AI-assisted changes, but the authorship note itself is not a defect and should not be removed. |
| DFHack automation primitives and Dreamfort are underused | **Rejected as stated** | Standing automation is configured in `onMapLoad.init`; Antfarm explicitly drives the vendored `library/dreamfort.csv` using Quickfort. DFHack's official 0.47.05-r8 library guide describes Dreamfort as a self-sustaining fortress blueprint with workshops, stockpiles, farming, defenses, hospital, jail, and rooms. Audit individual modules for duplication, but do not replace the current Quickfort/Dreamfort integration wholesale. |
| No clear comparison/interoperability with df-ai | **Valid documentation opportunity** | README credits df-ai and names the watchdog code borrowed from it, but does not clearly explain that Antfarm's differentiator is streaming presentation, audience interaction, and orchestration around a pre-existing build rather than being a drop-in replacement for df-ai's all-in-one automation. |
| MCP/agent-control ecosystem not used | **Future option; do not adopt uncritically** | A read-only semantic adapter could expose the existing state and event feed. However, the inspected `dwarf_fortress_mcp` repository explicitly says its compatibility registry is empty and no live mutation RPC is admitted in its current status. Its architecture is useful research, not a ready-to-deploy replacement for this 0.47.05 bridge. |
| No rate limiting on Director camera mode changes | **Partly stale / not demonstrated** | Director target changes already have a 150-point hysteresis threshold and a 10-second minimum follow duration; viewer camera grabs have a 20-second global cooldown and explicit overrides. `set_mode()` itself has no debounce, but mode selection is explicit (dashboard/moderator), not automatically toggled by each event. Add a mode-change limiter only if telemetry demonstrates real mode flapping. |
| No OBS WebSocket integration | **Valid gap** | The dashboard is designed for OBS capture, but there is no WebSocket client, scene switching, or stream-state automation in the repo. OBS documents WebSocket control as built in since OBS Studio 28; authentication should remain enabled. |
| Linux settings are not validated at launch | **Valid gap** | README and `AGENTS.md` document load-bearing OpenGL/renderer/TWBT settings, and warn that graphics packs can override per-save init files. `start_antfarm.sh` does not perform a preflight check for those settings before launch. A warning-only validator is safer than silently rewriting user configuration. |

## Adversarial follow-up review — 2026-10-31

A second reviewer (DeepSeek) challenged the conclusions and proposed an order for
the next work. I checked those assertions against the current source rather than
accepting them as instructions:

| Challenge | Re-check against code | Decision |
| --- | --- | --- |
| The Director may still ignore structured state and use opaque event scores | **Not true as phrased.** `_on_state_received()` passes each validated snapshot into `EventEngine.process_state()`, which derives job-start/finish, combat, stress, announcement, migrant-arrival, departure, and corroborated-death events. `score_citizen()` uses snapshot stress/profession/density, knowledge-graph degree, and decaying event weights. The scoring is heuristic, but its inputs and formula are visible and are documented in `calculate_interest_score()`. | Keep a score-breakdown/explainability view as a possible P2 enhancement; do not claim the Director is disconnected from structured state. |
| A minimal danger-response policy is a P1 omission | **Partly stale.** `_on_state_received()` already triggers `antfarm_lever` for DFHack-classified danger pauses, throttled to 30 seconds. The Lua module pulls only explicitly named defensive levers, checks for existing pull jobs, and applies its own 30-second per-lever throttle. Existing Python tests cover the danger-to-lockdown command. | The baseline lockdown exists. Broader tactics (burrow evacuation, squad movement, threat-specific responses) remain unimplemented or unverified and need a disposable/live-fort test plan. |
| The custom blueprint walker sits beside Quickfort | **True but not an architectural objection.** `antfarm_blueprint.lua` is a 22-step scheduler/gate wrapper; it delegates each map operation to Quickfort and the vendored Dreamfort catalogue. | Keep the wrapper; add a static contract test against real Quickfort labels and later semantic postconditions. |
| The offline suite should check the Dreamfort plan/catalogue | **Correct and actionable.** | Added the 22-step label contract test to the no-game suite. |
| Multiple save folders can make unattended startup continue the wrong fort | **Confirmed and safety-relevant.** `world_state()` and `fort_region()` previously returned the first glob match. | Launcher now fails closed on ambiguous saves; explicit selection is supported for existing forts via `ANTFARM_REGION`. Selecting one of several generated `world.dat` worlds remains manual because the current title-screen driver does not target `start_savegames` by folder name. |
| Python dependencies should be reproducible | **Confirmed.** Only `textual` and `rich` are imported as third-party runtime packages, but CI previously installed unpinned latest versions. | Add a Python 3.12 requirements lock using the exact dependency resolution from the passing CI run and consume it in CI and README setup. |
| Live-game smoke testing should follow | **Correct direction, but not the first safe patch.** DFHack 0.47.05 can be reached with local `dfhack-run`; however, the repository's own safety guide documents a prior test command reaching a real dwarf. Popup automation and blueprint completion depend on viewscreen/map timing. | Design an opt-in harness around a dedicated disposable save and an explicit operator-provided game directory. Do not add an auto-running CI job or mutate the operator's default save. |

This adversarial pass changed the immediate implementation order: the catalogue
contract, ambiguous-save guard, and dependency lock are being landed before a
live-game harness. The reviewer was right about those gaps, but the Director and
baseline danger-lockdown critiques needed correction.

## Additional improvement opportunities

These are additional findings from the current implementation, beyond the prior checklist.

1. **IPC protocol validation — addressed in PR #6.** `DFClient` validates the
   protocol-2 envelope and structured field types before publishing; malformed
   and unknown-version frames are rejected without replacing the last good state.
2. **Bound Twitch cooldown memory — addressed in PR #6.** Per-viewer timestamps
   use monotonic time, opportunistic expiry, and a 2,048-entry fail-closed cap;
   active viewers are not evicted to admit a burst of new logins.
3. **Subsystem freshness and omissions — addressed in PR #9.** The Lua aggregator
   publishes per-module report status, last-success age, mapping errors, and
   independent tick errors; the dashboard renders unhealthy/stale modules.
4. **Dreamfort catalogue drift — addressed in PR #7.** A static contract parses
   all 22 Lua plan entries and checks their executable Quickfort labels against
   the vendored Dreamfort CSV.
5. **Reproducible Python dependencies — addressed in PR #7.** `requirements.txt`
   pins the Textual/Rich runtime and resolved transitive dependencies used by
   Python 3.12 CI and README setup.
6. **Historical automation status — addressed in PRs #5 and #7.**
   `AUTOMATION-GAPS.md` is explicitly marked as historical research; the
   README, `CLAUDE.md`, `AGENTS.md`, and roadmap now describe current code and
   the multi-save limitation.
7. **Ambiguous save selection — addressed in PR #7.** The launcher refuses to
   select the first glob match when several saves exist, and supports explicit
   `ANTFARM_REGION` selection of an existing fort. Multiple generated worlds
   still require a manual Start Playing choice because the title-screen driver
   does not select them by save-folder name.
8. **Manager-order root-cause evidence — improved in PRs #11 and #12.** The
   read-only audit reports tri-state validated/active flags, stalled jobs,
   unmet item requirements, and whether the appointed manager owns a defined
   chair-room once the 20-citizen threshold applies. This diagnoses the leading
   office hypothesis but does not prove the historical 61-order incident's
   cause without that save's original state.
9. **Quarters furniture ordering and bed readiness — addressed in PR #14; CI
   passed.** The invalid `INORGANIC` material field is omitted; the request uses
   the vendored DFHack `workorder.lua` `__reduce_amount` matcher, which reduces
   equivalent open-order demand toward the requested target. Submission is only
   reported on `CR_OK`. Bed construction is gated on a free finished BED item,
   accessory orders are independent of bed shortfall, and the tick submits
   workshop targets before scheduling construction. The 17-case quarters Lua
   suite passed; no live-fort completion is claimed.
10. **Disposable live-smoke harness — implemented and exercised read-only.**
    PR #16 added `tools/live_smoke.py`; PR #19 records the first successful
    operator run against a separately copied `region_smoke` save on 2026-10-31.
    It required the marker, two explicit operator confirmations, loaded-map
    identity match, and completed the order, quarters and checklist reports.
    Captured baseline: 7 citizens, 0 beds, 4 manager orders (all validated),
    0 stalled jobs, 0 unmet requirements, manager office `not_required`,
    checklist 10 pass / 4 fail / 5 todo / 0 warn. It was read-only and did not
    prove production completion or survival; the live probe remains excluded
    from CI. See [LIVE-SMOKE.md](LIVE-SMOKE.md).

11. **Brewing job priority used a nonexistent job token — fixed in PR #20.**
    The checked-in 0.47.05 init prioritized `Brew`, but the operator's live
    `prioritize -r` output did not contain that job type. The actual plant
    brewing jobs are `CustomReaction` jobs with reaction names
    `BREW_DRINK_FROM_PLANT` and `BREW_DRINK_FROM_PLANT_GROWTH`. The init now
    scopes `CustomReaction` priority to those names via DFHack's documented
    `--reaction-name` option; farm/food job priorities remain a separate command.
    This does not create the corresponding manager orders.

12. **Dreamfort order import could be falsely marked complete — fixed in PR #21.**
    `antfarm_blueprint.lua` previously set `orders_done[lib]` before checking
    DFHack's return code. A rejected import could therefore be skipped forever.
    It now marks completion only on `CR_OK`, logs failure, and retries after a
    later completed build step. This fixes future failures; a previously persisted
    `orders_done.library/basic=true` in an existing plan still needs explicit
    operator inspection/recovery.

13. **Autolabor settings could be reported successful when DFHack rejected them —
    fixed in PR #22.** The sustenance module treated a non-throwing `pcall` as
    command success. It now checks `CR_OK` for MINE, CUTWOOD, HERBALIST and PLANT
    and surfaces rejected settings in subsystem notes. This confirms the setting
    command was accepted, not that every citizen has eligible/reachable work.

## Research references

- [DFHack 0.47.05-r8 Core / `dfhack-run`](https://docs.dfhack.org/en/0.47.05-r8/docs/Core.html): external commands can be sent to an already-running game; the documented RPC listener is local and uses TCP port 5000.
- [DFHack 0.47.05-r8 Quickfort blueprint library](https://docs.dfhack.org/en/0.47.05-r8/docs/guides/quickfort-library-guide.html): documents Dreamfort's full-fort scope and official blueprint catalogue.
- [DFHack 0.47.05-r8 `prioritize`](https://docs.dfhack.org/en/0.47.05-r8/docs/tools/prioritize.html): job types can be boosted, and `CustomReaction` can be scoped by reaction name.
- [DFHack 0.47.05-r8 `autolabor`](https://docs.dfhack.org/en/0.47.05-r8/docs/tools/autolabor.html): labor allocation is constrained by eligible jobs and excludes certain military/burrow assignments.
- [DFHack 0.47.05-r8 `workNow`](https://docs.dfhack.org/en/0.47.05-r8/docs/tools/workNow.html): `workNow 2` requests assignment after job completion; it does not create work.
- [DFHack `dfhack-mcp`](https://github.com/alexanderolvera/dfhack-mcp): read-oriented semantic inspection/actuator design, with mutation gated behind explicit configuration.

- [Ben Lubar's df-ai repository](https://github.com/BenLubar/df-ai) and [0.47.05-r1 release notes](https://github.com/BenLubar/df-ai/releases): relevant prior art for 0.47.05 military, logistics, and screen handling.
- [OBS Remote Control Guide](https://obsproject.com/kb/remote-control-guide): WebSocket control is included in OBS Studio 28+ and should be password protected.
- [`dwarf_fortress_mcp` README](https://github.com/Dicklesworthstone/dwarf_fortress_mcp) and [implementation status](https://github.com/Dicklesworthstone/dwarf_fortress_mcp/blob/main/IMPLEMENTATION_STATUS.md): useful semantic-control architecture, with explicit compatibility and live-mutation limitations in the current implementation status.

---

The working rule from this review: **validate against the checked-in code and a live game before treating an architectural proposal as a task.** Fix small, measurable reliability errors first; keep risky DF 0.47 memory writes behind manual verification.
